Что это

Claude Code можно вынести из открытого терминала и поставить на повторяющееся обслуживание кода: искать механические дефекты, проверять их и открывать PR. Боль здесь в задачах, которые никто не хочет брать руками, но которые копятся каждый день. Раньше для повторения приходилось держать /loop в живой сессии, запускать локальные задания на своей машине или самому собирать cron и обвязку. Облачная рутина сохраняет запрос, репозитории и подключённые сервисы, а запускает работу по расписанию, HTTP-вызову или событию GitHub в инфраструктуре Anthropic, даже когда компьютер выключен.

Как работает

Ты один раз задаёшь запрос, репозитории, подключённые сервисы и способ запуска. Вариантов три: расписание, API-вызов и событие GitHub; их можно совмещать у одной рутины. Каждый запуск создаёт отдельную облачную сессию Claude Code. Код берётся из свежего клона выбранного репозитория, поэтому локальные файлы и незакоммиченные изменения в такую работу не попадают. По умолчанию Claude может отправлять изменения только в ветки с префиксом claude/, если отдельно не разрешить отправку в другие ветки. Подключённые сервисы дают ему доступ к внешним системам, причём во время облачного запуска подтверждений перед действиями нет. От /loop это отличается тем, что /loop живёт внутри текущей сессии и на твоей машине, а облачная рутина переживает закрытый терминал и перезапуск компьютера. Для задач с локальными файлами ближе локальные задания Claude Code Desktop, а для облачных routines нужно учитывать лимиты запусков и расход обычного лимита Claude Code.

Пример

В открытой сессии Claude Code введи /schedule daily PR review at 9am. Claude проведёт тебя через настройку и сохранит облачную рутину с ежедневным расписанием. Затем введи /schedule list, чтобы увидеть её в списке.

Как проверить

После сохранения команда /schedule list должна показать созданную рутину. Когда она запустится, в списке сессий появится отдельная сессия запуска, где можно посмотреть действия Claude и подготовленные изменения.

Где споткнёшься

  • Облачный запуск получает свежий клон выбранного репозитория, а не твои локальные файлы и незакоммиченные изменения.
  • По умолчанию отправка изменений разрешена только в ветки с префиксом claude/; существующую рабочую ветку рутина не тронет без отдельного разрешения.
  • Время расписания берётся из твоего часового пояса, но запуск может сдвинуться на несколько минут из-за распределения нагрузки.
  • Подключённые сервисы добавляются по умолчанию, а облачная рутина может писать через них без запроса разрешения — лишние подключения нужно убрать вручную.

Слои достоверности

01 Boris Cherny (@bcherny) · в оригинале

Boris Cherny (@bcherny) — в профиле указано «Claude Code @anthropicai». В загруженном фрагменте он пишет, что несколько недель пробует передать Claude повседневное обслуживание приложений и видит первые признаки того, что это может сработать; также назван Slack-канал proj-claude-maintains-apps. Текст обрывается на фразе «In it, Claude», поэтому каталог задач, правила проверки, число PR и результат в процентах в оригинале не прочитаны и автору поста приписывать их нельзя.

02 @CarolinaCherry · дописано на сайте

Автор сайта @CarolinaCherry развернул этот обрывок в подробную схему из одиннадцати задач обслуживания: от поиска падений и мёртвого кода до упрощения логики и исправления нестабильных тестов. Он добавил двухэтапную проверку мёртвого кода, таблицы истинности и формальное моделирование логики, идею настраивать саму рутину вместо каждого PR, а также статистику по открытым и влитым PR. Сайт также ссылается на страницу routines на домене claude.ai; этот домен я не проверял.

03 code.claude.com · документация

Официальная документация подтверждает сам механизм облачных routines: сохранённый запрос, репозитории, подключённые сервисы, запуск по расписанию, API или GitHub-событию, отдельные сессии и работу без включённого компьютера. Она также описывает /schedule, свежий клон репозитория, ограничения веток, отсутствие подтверждений во время запуска и расход лимитов. Не удалось подтвердить по официальной документации, что Boris Cherny использует именно одиннадцать перечисленных задач, Slack-схему из поста, двухдневный probe, таблицы истинности, показатель 46% или самонастройку routines.

Расхождения с документацией

сайт обещает то, чего документация не подтверждает
  • Что у Boris Cherny работают именно одиннадцать названных routines: crash fuzzer, ant-only shipper, logic simplifier, logic bugfixer, dup unifier, dead-code removal, useless-test pruner, shipped-feature inliner, flaky-test fixer, abstraction improver и abstraction police.
  • Что эти задачи запускаются отдельно для iOS, Android, Desktop, web, CLI и Agent SDK, а результаты складываются в Slack-канал proj-claude-maintains-apps.
  • Что для мёртвого кода используется двухдневная схема: сначала добавить logging, подождать день, затем удалить то, что не сработало, и что эту схему Claude придумал сам.
  • Что каждый PR обязан запускать /verify и содержать repro, truth table и формальную модель логики, а проверки идут на реальных приложениях без mocks.
  • Что за несколько недель 388 открытых PR дали 180 merged, то есть 46%, и что перед человеческой проверкой каждый PR проходит отдельный Claude Code Review.
  • Что Claude сам настраивает routine по ошибкам предыдущего запуска, а Tag умеет создавать такие routines.
